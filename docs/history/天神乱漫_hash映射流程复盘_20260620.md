## 1. 复盘结论

本次任务最终将 `.alst` 验证后的文件名覆盖率提升到：

```text
36092 / 36829 = 98.00%
```

最重要的经验是：

```text
不要先做大规模盲目候选爆破。
应先找到“真实文件名保存在哪里”，再用原游戏 hasher 验证。
```

对这类 PackinOne/Hxv4 hash 化 XP3 游戏，最优路线不是“从 XP3 index 反推文件名”，也不是“人工跑完游戏流程”，而是：

```text
XP3 hash 文件表
  + 原游戏 hasher
  + 脚本/PSB/INI/FUNC 内部真实名
  + 包级命名规则
  + 运行时 storage API trace
  -> 统一 manifest
```

其中最大突破是 SCN JSON 内部名恢复。该步骤将覆盖率从：

```text
15877 / 36829 = 43.11%
```

提升到：

```text
35178 / 36829 = 95.52%
```

下一次同类任务中，这一步应在基础工具链打通后立即执行，而不是放到中后期。

## 2. 本次流程中的低效点

### 2.1 过早进入广义候选爆破

早期做了大量规则扩展：

- BGM 编号。
- EV 编号。
- 语音编号。
- 扩展名组合。
- 路径前缀组合。

这些方法能带来收益，但候选量大、无效项多，而且覆盖率提升有限。它们适合作为补缺手段，不适合作为第一主线。

下次应把它们后移到“高价值来源已处理完之后”。

### 2.2 SCN/PSB 内部名恢复做得太晚

本次直到覆盖率 43.11% 后，才系统处理 `scn_hash_json`。结果这一轮直接提升到 95.52%。

这说明大量真实名不是藏在 EXE，也不是需要运行全流程才出现，而是已经在可反编译的 SCN/PSB JSON 里。

下次应尽早做：

1. 解出 `scn.xp3` hash 文件。
2. 批量反编译 SCN PSB。
3. 读取 JSON 根节点 `name`。
4. 遍历 `voice/file/bg/storage/movie` 等字段。
5. 送入原 hasher。

### 2.3 对“日志行数”和“真实覆盖率”的区分不够早

`FileNameHash.log` 里会包含大量候选探测结果。日志行数增加，不代表 XP3 包内真实文件被映射。

下一次必须从第一天就使用两套指标：

- hash 知识库规模：`FileNameHash.log` 唯一行数。
- 真实覆盖率：`.alst` 中能被 `FileNameHash.log + DirectoryHash.log` 命中的比例。

报告和决策只应以第二个指标为准。

### 2.4 运行时 trace 应作为补缺，不应作为早期主力

`TVPGetPlacedPath` / `TVPCreateIStream` trace 很有价值，但只有在进入具体游戏流程或 UI 页面时才有高收益。

标题阶段 trace 主要验证机制，对覆盖率提升有限。

下次应将 trace 用于：

- CG 鉴赏。
- BGM 鉴赏。
- 语音收藏。
- 存读档。
- 系统设置。
- 流程图。
- 回想模式。

而不是只停留在标题画面。

## 3. 下一次任务推荐流程

### 3.1 阶段 0：建立工作目录与命名规范

建议目录结构：

```text
work\<game_id>\
  logs\
  candidates\
  backups\
  extracted\
  restored\
  decompiled_scn\
  reports\
  scripts\
```

每轮探测都应保存：

- 候选生成脚本。
- 候选列表。
- 候选统计 JSON。
- 探测前 hash 日志备份。
- 探测后合并日志备份。
- 本轮 manifest stats。

建议每轮命名格式：

```text
hash_log_backup_before_<stage>_YYYYMMDD_HHMMSS
hash_log_backup_after_<stage>_merged
<stage>_candidates.json
<stage>_probe_candidates.txt
<stage>_candidates_stats.json
```

### 3.2 阶段 1：先解 XP3 hash 文件表和 `.alst`

目标：

```text
先知道包里到底有哪些 dir_hash/file_hash。
```

步骤：

1. 使用 Cxdec/GARbro/专用工具解出 XP3 文件表。
2. 对每个包生成 `.alst`。
3. 保存 hash 文件到 `Extractor_Output\<package>\...`。
4. 不要求此时知道真实文件名。

产物：

```text
bgimage.alst
bgm.alst
data.alst
data_hgl.alst
evimage.alst
fgimage.alst
main.alst
scn.alst
uipsd.alst
video.alst
voice.alst
```

验收标准：

- 能统计每个包 `.alst_total`。
- 能列出未命名文件 hash。
- 能读取 hash 文件头，判断 PNG/JPG/OGG/PSB/UTF-16 等类型。

### 3.3 阶段 2：打通原游戏 hasher

目标：

```text
用游戏自己的规则完成“文件名 -> hash”。
```

步骤：

1. 注入 hash dumper。
2. hook 文件名 hasher 和目录名 hasher。
3. 记录：

```text
DirectoryHash.log
FileNameHash.log
Universal.log
```

4. 实现批量 probe：

```text
HashProbeCandidates.txt -> TVPIsExistentStorage() -> FileNameHash.log
```

5. 每轮 probe 前备份旧日志。
6. 每轮 probe 后合并去重。

验收标准：

- 输入一个已知文件名，例如 `bgm01.ogg`，日志能出现对应 hash。
- 输入空目录或常见目录，`DirectoryHash.log` 能记录。
- manifest 能将 `.alst` 条目映射到真实文件名。

### 3.4 阶段 3：立刻处理 SCN/PSB JSON

这是下次任务最应前置的关键阶段。

目标：

```text
从剧情脚本内部直接拿真实文件名，而不是先猜。
```

步骤：

1. 找到 `scn` 包里的所有 hash 文件。
2. 用 Ulysses/FreeMote 批量反编译：

```powershell
PsbDecompile.exe -t Scn -e SHIFT-JIS -indent -o <out> <input>
```

3. 保存到：

```text
work\<game_id>\decompiled_scn
```

4. 遍历 JSON：
   - 根节点 `name`。
   - `voice` 字段。
   - `file` 字段。
   - `filename` 字段。
   - `image` 字段。
   - `bg` 字段。
   - `storage` 字段。
   - `movie/video` 字段。
   - `rule` 字段。
5. 对不同字段做最小必要扩展：
   - voice -> `.ogg`、`.ogg.sli`
   - BGM -> `.ogg`、`.ogg.sli`
   - BG -> `.png`、`.jpg`
   - EV -> `.png`、`.psb`、`.pimg`
   - script -> `.ks`、`.ks.scn`
6. 将候选交给原 hasher。
7. 重建 manifest。

预期收益：

- 通常会一次性覆盖大部分剧情脚本、语音、背景、CG。
- 本次实测对应阶段从 43.11% 提升到 95.52%。

下次应将此阶段放在 20%-40% 覆盖率之前完成，避免走弯路。

### 3.5 阶段 4：内容反推，而不是外部猜名

对未命名 UTF-16/TJS/INI/FUNC/PSB 文件，应先读取内容。

本次 `uipsd` 的最佳方法是：

```text
解出 hash 文件内容
  -> 从内部 psd/incl/UI_PAGE/GetUIPSD 字段反推文件名
  -> 送入 hasher 验证
```

下次可推广到：

- UI INI/FUNC。
- 主系统 TJS。
- CG list。
- 回想 list。
- save/load list。
- HCG list。
- chart/flow list。
- thumbnail list。

执行步骤：

1. 按文件头筛选 UTF-16、PSB、文本类 hash 文件。
2. 解码或反编译。
3. 提取内部类名、页面名、psd 名、include 名、resource 字段。
4. 生成自身文件名和伴生文件名。
5. probe。
6. manifest 验证。

### 3.6 阶段 5：伴生文件规则

很多文件不在脚本里直接出现，而是由程序逻辑根据已知文件名派生。

优先规则：

```text
xxx.ogg      -> xxx.ogg.sli
xxx.stage    -> xxx.stand
xxx.asd      -> xxx.stand
bg_xxx.png   -> bgthum_bg_xxx.jpg
evxxxxaa.png -> thum_evxxxxaa.psb
```

执行步骤：

1. 从当前 manifest 中读取所有已命中文件名。
2. 按扩展名生成伴生名。
3. 对缩略图、立绘、PSB 采用包级规则。
4. 过滤已知日志。
5. probe。
6. manifest 验证。

本次伴生文件逻辑从 37.20% 提升到 43.11%，说明该阶段非常适合放在 SCN JSON 之前或之后的第一轮补强。

### 3.7 阶段 6：包级命名模型

不同包的命名规律不同，不应使用统一候选模板。

推荐策略：

| 包 | 优先方法 |
| --- | --- |
| `scn` | PSB/SCN JSON 根节点 `name` |
| `voice` | SCN `voice` 字段 + alst 前后缺号 |
| `bgimage` | SCN `file/bg` 字段 + alst 顺序家族模型 |
| `bgm` | SCN BGM 字段 + `.ogg.sli` |
| `evimage` | SCN CG 字段 + HCG list |
| `fgimage` | `imagemulti.txt`、`.stage`、`.stand` |
| `uipsd` | INI/FUNC 内部字段 |
| `video` | 目录序列帧模型 |
| `data_hgl` | HCG list、附加语音 list、PSB 内部事件组 |
| `data` | system/sysscn 文本内容、sound/SE 命名模型 |

下次应先给每个包分类，再决定候选生成方式。

### 3.8 阶段 7：alst 顺序缺口分析

当覆盖率已经很高时，剩余文件通常不是随机分布，而是出现在相邻已知文件之间。

方法：

1. 按 `.alst` 原顺序列出未映射条目。
2. 显示前后最近的已映射文件名。
3. 观察家族规律。
4. 只生成相邻范围内的候选。

示例：

```text
school_gate_c.png
<unknown>
<unknown>
<unknown>
school_gate_cherry_go_a.png
```

可推断方向：

```text
school_gate_cherry_a.png
school_gate_cherry_back_a.png
school_gate_cherry_back_b.png
```

本次最后一轮用该方法将 `bgimage` 从 120/153 提升到 150/153。

### 3.9 阶段 8：运行时 trace 只用于剩余缺口

当静态 JSON、内容反推、伴生规则、包级模型都处理后，再进入运行时 trace。

目标：

```text
抓“运行时拼出来，但静态文件里不显眼”的 storage name。
```

建议触发页面：

- 标题菜单。
- CG 鉴赏。
- BGM 鉴赏。
- 语音收藏。
- 存档。
- 读档。
- 设置。
- 流程图。
- 回想。
- 特典。

hook 层级：

```text
TVPGetPlacedPath
TVPCreateIStream
TVPIsExistentStorage
```

注意：

- 标题阶段 trace 只能验证机制。
- 必须过滤 `*.xp3>伪名`。
- 必须区分 probe 线程和真实游戏线程。

## 4. 标准化工具链建议

下一次任务应优先准备以下脚本。

### 4.1 manifest 构建脚本

功能：

- 读取 `.alst`。
- 读取 `DirectoryHash.log`。
- 读取 `FileNameHash.log`。
- 输出：
  - `hash_manifest.json`
  - `hash_manifest.tsv`
  - `hash_manifest_stats.json`
  - `unmapped_gap_details.json`

要求：

- 每轮 probe 后必须运行。
- 统计必须区分 `total` 和 `alst_total`。
- 覆盖率报告应以 `alst_fully_mapped / alst_total` 为准。

### 4.2 probe 自动化脚本

功能：

1. 停止旧游戏/loader 进程。
2. 备份当前 hash 日志。
3. 写入候选文件。
4. 启动 loader `--hash`。
5. 等待 `HashProbeDone:N`。
6. 停止进程。
7. 合并日志。
8. 重建 manifest。

必须避免：

- 直接覆盖旧日志不备份。
- 在日志未刷盘时强杀。
- 用部分日志重建 manifest。

### 4.3 候选来源脚本

推荐按来源拆分：

```text
collect_scn_json_candidates.py
collect_uipsd_content_candidates.py
generate_companion_candidates.py
generate_video_sequence_candidates.py
generate_bg_sequence_gap_candidates.py
generate_voice_gap_candidates.py
collect_main_text_resource_candidates.py
collect_psb_internal_event_candidates.py
```

不要把所有逻辑塞进一个大脚本。分来源保存候选，方便复盘每轮收益。

### 4.4 覆盖率时间线脚本

本次后期新增的只读统计脚本非常有用：

```text
compute_backup_coverage_timeline.py
```

下次应从一开始就使用。

作用：

- 对每个 `hash_log_backup_after_*_merged` 重新计算覆盖率。
- 避免报告中的历史覆盖率靠记忆。
- 能准确判断每轮候选是否真的提升 `.alst` 命中。

## 6. 覆盖率检查点

下一次可以用以下检查点判断流程是否健康。

### 6.1 20%-40%

应已经完成：

- 基础 hasher。
- 初始脚本候选。
- BGM/背景/部分语音。

如果低于 20%，优先检查：

- DirectoryHash 是否缺失。
- `.alst` 是否解析错误。
- FileNameHash 编码是否读错。
- hasher 是否实际触发。

### 6.2 60%-80%

应已经完成：

- SCN JSON 内部名。
- 大部分 voice。
- 大部分 scn。
- 大部分 bgimage/evimage。

如果仍低于 60%，说明还没有找到脚本内部真实名来源。

### 6.3 90%+

应开始做：

- 包级补缺。
- alst 顺序分析。
- 伴生文件。
- UI 内容反推。

不要再扩大普通候选爆破。

### 6.4 98%+

剩余缺口通常属于：

- 特殊系统文件。
- 运行时拼接名。
- UI 特定页面。
- 少量缺失/占位文件。
- 特殊 SE/BGM/语音。
- 未反编译 PSB 内部资源。

此时应对每个剩余 hash 做分类，不再追求单一大脚本解决全部问题。

## 7. 避坑清单

1. 不要把 `FileNameHash.log` 行数当覆盖率。
2. 不要不备份就运行 `--hash`，日志可能被重建。
3. 不要只看候选数量，必须看 `.alst` 命中增量。
4. 不要在日志未刷盘时强杀游戏。
5. 不要忽略 `.ogg.sli`，大量音频有伴生文件。
6. 不要只扫已恢复真实名目录，hash 文件本身也可能可反编译。
7. 不要晚处理 SCN/PSB JSON。
8. 不要对 `uipsd` 做随机猜名，优先读 INI/FUNC 内容。
9. 不要把 `xp3>伪名` 当真实 storage name。
10. 不要在高覆盖后继续扩大无差别编号范围。

## 9. 本次经验对下一次的核心改进

```text

再立刻处理 SCN JSON
再做伴生文件
```

最终判断：

```text

原游戏 hasher 是验证器。
.alst manifest 是裁判。
候选爆破只是补缺工具。
```
