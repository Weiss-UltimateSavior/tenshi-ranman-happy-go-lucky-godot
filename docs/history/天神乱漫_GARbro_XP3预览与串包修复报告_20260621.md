### A.2 判断 GARbro 需要解决的不是单纯解密

初始直觉可能是：

```text
GARbro 无法预览资源 = XP3 内容解密算法未实现
```

但后续验证表明，问题更准确地分为三层：

1. **文件名层**：XP3 index 中显示的是短 ID 或 hash，需要映射成真实文件名。
2. **数据位置层**：XP3 静态 `segm` offset / size 指向的可能不是实际资源，而是占位数据。
3. **GARbro 状态层**：GARbro 的加密方案对象可能被复用，需要防止不同 archive 的映射串包。

因此，GARbro 接入不能只写一个 `Decrypt()`；还要解决：

```text
短 ID -> file hash -> 真实文件名 -> Extractor_Output 真实源文件
```

### A.3 确认短 ID 规则

XP3 中出现的 `0050`、`0150`、`0250` 不是 hash，也不是真实文件名。

根据 `TenShiSouZou_short_id_hash_report.md`，短 ID 是 Cxdec 运行时 `FileEntry.Ordinal` 生成的 fake name：

```text
ordinalLow32 = Ordinal & 0xFFFFFFFF

do:
    ch = (ordinalLow32 & 0x3FFF) + 0x5000
    写入一个 UTF-16LE wchar
    ordinalLow32 >>= 14
while ordinalLow32 != 0
```

普通条目的对应关系：

```text
Ordinal 0 -> 0050
Ordinal 1 -> 0150
Ordinal 2 -> 0250
Ordinal 3 -> 0350
```

这个规则非常关键，因为 `.alst` 的顺序可以和 XP3 内短 ID 对齐，从而恢复：

```text
0150 -> 当前包第 1 个 .alst 条目 -> fileHash -> 真实文件名
```

注意：短 ID 只在当前 archive 内有意义。同一个 `0150` 在不同包中可以对应完全不同文件：

```text
bgm.xp3     0150 -> bgm01.ogg
evimage.xp3 0150 -> ev0101a.png
voice.xp3   0150 -> 某条语音
```

这也是后续串包 bug 的根本背景。

## 3. 现象一：3KB PNG 无法预览的原因

### 3.1 直接原因

`evimage.xp3` 的静态 XP3 index 中，若直接按 `segm` 记录读取数据，会得到约 3KB 的块。这些块不是实际 PNG 图像内容。

实际观察到的情况包括：

- 多个条目指向相同或异常的 offset / size。
- 例如部分条目读出的大小约为 `3537` 字节。
- 这些数据不具备有效 PNG 图像结构，因此 GARbro 预览失败，提取出的 `.png` 也无法打开。

### 3.2 根本原因

该游戏的 Hxv4 / PackinOne / Cxdec 资源机制并不依赖 XP3 静态 index 中的真实文件名和真实数据位置来完成普通文件枚举。真实资源与真实文件名需要结合运行时 hash 逻辑、`.alst` 文件、已捕获的 hash 映射、以及 `Extractor_Output` 中的解出文件来还原。

因此，对这个游戏而言：

```text
GARbro XP3 index 读取到的 offset / size
!=
实际可预览资源的位置
```

有效 PNG 实际存在于：

```text
E:\Galgame\天神乱漫 Happy GO Lucky!!\Extractor_Output\evimage\<目录hash>\<文件hash>.png
```

示例：

```text
E:\Galgame\天神乱漫 Happy GO Lucky!!\Extractor_Output\evimage\94D4A97C61498621\74DF670D310AE5301CC8DCB6B21371EF1846082C509F2AA69C17D59A814C3C32.png
```

该文件验证为标准 PNG：

```text
Header: 89 50 4E 47 0D 0A 1A 0A
Length: 2360584
```

## 4. 现象二：evimage.xp3 显示成 OGG 的原因

### 4.1 用户侧现象

打开：

```text
E:\Galgame\天神乱漫 Happy GO Lucky!!\evimage.xp3
```

但 GARbro 列表显示：

```text
bgm01.ogg
bgm01.ogg.sli
bgm02.ogg
bgm02.ogg.sli
...
```

这明显不符合 `evimage.xp3` 的内容。

### 4.2 已排除项

检查 `evimage.namecache` 后确认其内容正确：

```text
0150##YSig##ev0101a.png##YSig##evimage/94D4A97C61498621/74DF670D310AE5301CC8DCB6B21371EF1846082C509F2AA69C17D59A814C3C32.png
0250##YSig##ev0101b.png##YSig##evimage/94D4A97C61498621/5B5694A1FB5B2C83AF235F771BCCAF9E922422343FE2D2136666E87ABEEFAA62.png
```

同时 `bgm.namecache` 中确实存在：

```text
0150##YSig##bgm01.ogg
0250##YSig##bgm01.ogg.sli
0350##YSig##bgm02.ogg
```

因此，问题不是 `evimage.namecache` 被错误写成 BGM，而是 GARbro 打开 `evimage.xp3` 时仍在使用上一次 archive 的内存映射。

### 4.3 根本原因

GARbro 的 XP3 加密方案对象可能被复用。此前 `TenshiSxCxCrypt` / `TenshiSzCrypt` 内部状态包含：

- `m_archive_path`
- `m_filename_map`
- `m_dirpath_map`
- `m_archive_cache_map`
- `m_archive_source_map`
- `m_external_file_map`

原逻辑中，`SetArchivePath()` 只更新路径：

```csharp
m_archive_path = archivePath;
```

`Init()` 中也只有在 `m_filename_map == null` 时才加载映射。

这导致一个复用场景：

```text
打开 bgm.xp3
  -> 加载 bgm.namecache
  -> m_filename_map["0150"] = "bgm01.ogg"

再打开 evimage.xp3
  -> archive path 变化
  -> 但 m_filename_map 不为空
  -> 不重新加载 evimage.namecache
  -> 0150 继续显示 bgm01.ogg
```

## 5. 修复内容

## 5.1 增加 Hxv4 PackinOne 下拉项

在 `ArcXP3.cs` 中加入下拉项：

```csharp
yield return new KeyValuePair<string, ICrypt> (
    "天神乱漫 Happy GO Lucky!! (Hxv4 PackinOne)",
    new TenshiSxCxCrypt());
```

作用：

- 使 GARbro 的资源文件识别下拉菜单中可以直接选择该游戏方案。
- 避免用户只能依赖不稳定的自动识别。

## 5.2 OpenEntry 优先使用外部真实文件

在 `ArcXP3.cs` 的 `OpenEntry()` 中加入：

```csharp
var tenshi = xp3_entry.Cipher as TenshiSzCrypt;
if (tenshi != null)
{
    var external = tenshi.OpenExternalEntry (xp3_entry);
    if (external != null)
        return external;

```

作用：

- 当当前条目能在 `Extractor_Output` 中找到真实源文件时，GARbro 预览和提取直接打开真实文件。
- 避免继续使用 XP3 静态 index 中的 3KB 占位块。

## 5.3 namecache 支持第三列源文件路径

原缓存格式：

```text

```

新缓存格式：


```text

```

新增字段：

```csharp
private Dictionary<string, string> m_archive_source_map;
private Dictionary<string, string> m_external_file_map;
```

作用：

- `m_archive_source_map`：保存当前 archive 的 cache key 到真实源文件路径。
- `m_external_file_map`：保存显示名到真实源文件路径，供 `OpenExternalEntry()` 使用。

## 5.4 旧两列缓存自动升级

修复后逻辑为：

```text
加载 namecache
  如果 cache 内已有 source path：
    直接使用
  如果 cache 只有两列，没有 source path：
    继续读取 .alst 和 Extractor_Output
    重建带第三列的新 cache
```

作用：

- 避免旧缓存阻止新逻辑生效。
- 用户不需要手动删除旧 `.namecache`。

## 5.5 支持无扩展名 hash 源文件

部分解出的真实文件位于：

```text
Extractor_Output\<archive>\<dirHash>\<fileHash>
```

即没有 `.png`、`.ogg` 等扩展名。

因此 `GetExtractedSourcePath()` 增加了以下查找顺序：

1. `<fileHash><显示名扩展名>`
2. `<fileHash>`
3. 递归查找 `<fileHash>.*`
4. 递归查找 `<fileHash>`

作用：

- 修复 `bgimage`、`bgm`、`fgimage`、`voice` 等包中真实文件无扩展名时无法绑定源文件的问题。
- 使 GARbro 预览和提取更接近 Cxdec 已解出结果。

## 10. 当前方案性质

当前 GARbro 支持方式属于：

```text
XP3 短 ID / hash 名显示修复
+ Extractor_Output 真实文件旁路预览
```

也就是说，GARbro 仍然使用 XP3 index 做条目枚举，但在实际打开条目时，优先使用 `Extractor_Output` 中已经由 Cxdec 解出的真实文件。

该方案的优点：

- 实现成本低。
- 对 GARbro 原有 XP3 框架侵入较小。
- 能立即解决预览和提取 3KB 占位块的问题。
- 能利用已建立的 `.alst`、`.namecache`、hash 映射结果。

该方案的限制：

- 如果某个资源没有在 `Extractor_Output` 中解出，GARbro 仍无法凭 XP3 静态 index 直接得到真实内容。
- 这不是完整复刻 Hxv4 / PackinOne 运行时索引和数据定位逻辑。
- 对于尚未绑定 source path 的条目，后续仍需要继续完善 extractor 输出或进一步逆向真实数据定位逻辑。

## 11. 后续优化建议

1. 将 `.namecache` 生成流程整理为独立工具，避免手工 PowerShell 脚本重复执行。
2. 为每个 archive 统计：
   - XP3 条目数
   - namecache 命名命中数
   - source path 命中数
   - 可预览条目数
3. 继续研究 Hxv4 / PackinOne 的真实数据定位逻辑，减少对 `Extractor_Output` 的依赖。
4. 在 GARbro 中增加调试日志开关，显示当前 archive 实际加载的 `.namecache` 文件路径，方便排查串包或缓存污染。
5. 对 `voice`、`bgm` 等音频包继续验证 GARbro 的音频预览链路，确认文件流正确后是否还需要 OGG / SLI 特殊处理。

## 12. 完整流程结论

本阶段工作从“hash 值与文件名映射已经基本完成”继续推进到“GARbro 可打开、显示真实文件名、预览真实资源，并修复实际使用中暴露出的错误”。

完整成果可以分为四层：

1. **映射层**：将前置阶段得到的 `FileNameHash.log`、`DirectoryHash.log`、`.alst`、SCN JSON 解析结果转化为 GARbro 可快速读取的 per-archive `.namecache`。
2. **短 ID 层**：确认并实现 `0050`、`0150`、`0250` 这类 XP3 内短 ID 到 `.alst` ordinal 的对应关系，使 GARbro 能把短 ID 显示成真实文件名。
3. **预览层**：发现 XP3 静态 index 中的 `segm` 数据并非真实资源后，改为通过 `.namecache` 第三列指向 `Extractor_Output` 中的真实源文件，解决 3KB 无效 PNG 问题。
4. **稳定性层**：修复旧缓存无 source path、无扩展名 hash 源文件无法绑定、GARbro scheme 对象复用导致不同 archive 映射串包等问题。

本次最终解决了两个用户可见的关键错误：

1. `evimage.xp3` 预览/提取到 3KB 无效 PNG，是因为 XP3 静态 index 中的数据不是实际资源内容。通过 `Extractor_Output` 源文件旁路打开，已可获得真实 PNG。
2. `evimage.xp3` 全部显示成 `bgm*.ogg`，是因为 GARbro 复用了加密方案对象且没有在 archive 切换时清空旧映射。通过 `ResetMappings()` 和 archive path 变化检测，已修复串包。

当前 `evimage.xp3` 应能正确显示为 `ev*.png` 并支持预览。`bgimage` 等无扩展名源文件的预览路径也已补充支持。

从方法论上看，本项目不是“单纯给 GARbro 加一个 XP3 解密算法”，而是把前置 hash 映射工程、短 ID ordinal 规则、Cxdec 提取结果和 GARbro 打开流程组合起来，形成了一条可复用路线：

```text
先完成 hash/文件名映射
再把映射压缩成当前 archive 可快速读取的 cache
再让 GARbro 负责显示和交互
最后绕过 XP3 静态占位数据，打开真实 Extractor_Output 文件
```

这条路线适合继续迁移到其它 Hxv4 / PackinOne / Cxdec 类游戏。
