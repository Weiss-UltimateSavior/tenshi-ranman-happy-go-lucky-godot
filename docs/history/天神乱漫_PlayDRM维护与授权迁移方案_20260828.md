# 天神乱漫 Happy Go Lucky!! PlayDRM 维护与授权迁移方案

日期：2026-08-28  
适用对象：拥有作品著作权、发行权及授权系统处置权限的项目组

## 1. 结论

旧日文版的 `tenshin_hgl.exe` 是独立的 Kirikiri 发行入口，在进入游戏内容前会调用
PlayDRM 授权流程。该流程属于封闭的第三方访问控制组件。不能将汉化补丁中的 EXE/DLL
作为替换、伪造或跳过旧授权的技术依据，也不应对闭源二进制实施补丁发行。

面向公司的可维护解决方案是重新发行：保留原始内容包，使用公司可审计的启动器、授权
模块和签名更新包组成新的日文发行入口。旧版仅作为兼容性参照，不作为新发行版的补丁
目标。

## 2. 已确认的安装结构

原版根目录：

`E:\Galgame\天神乱漫 Happy GO Lucky!!`

重要文件及职责：

| 文件 | 角色 | 维护结论 |
| --- | --- | --- |
| `tenshin_hgl.exe` | 原始日文 Kirikiri 运行时入口 | 保留原始文件，不修改。 |
| `data.xp3`、`scn.xp3`、`voice.xp3` 等 | 日文脚本、图像、声音与系统资源包 | 可作为内容资产清单和完整性校验对象。 |
| `天神乱漫 Happy GO Lucky!!.exe` | 不同的汉化发行入口 | 仅用于识别不同发行链路，不能作为日文版授权组件。 |
| `ShiraYukiNoa.dll`、`tenshin_chs.xp3` | 汉化版组件 | 不应纳入日文维护版。 |
| `天神乱漫 Happy Go Lucky!! 日文维护版.exe` | 新增的维护启动器 | 目前只负责启动原始日文 EXE，不改变其授权状态。 |

## 3. 禁止纳入实施的做法

- 修改旧 EXE 的条件跳转、导入表、校验值或验证结果。
- 利用汉化 DLL 模拟、替换或截获 PlayDRM 的调用。
- 构造许可证、设备标识、在线响应或离线令牌。
- 以二进制差分形式发行针对旧 PlayDRM 的补丁。

这些做法不可审计、不可长期维护，也会使公司无法证明新发行版的授权边界和供应链完整性。

## 4. 推荐实施路径：受控重发行

### 4.1 第一阶段：权利与材料归档

1. 将原始发行母版、可用源代码、构建机、代码签名证书和 PlayDRM 合同/SDK 归档。
2. 由法务或发行负责人确认：是否仍能向原 PlayDRM 厂商申请许可证迁移、离线激活重签或
   旧授权服务恢复。
3. 为所有 XP3 包建立 SHA-256 清单，并保留独立的日文资源清单；不混入汉化资源。
4. 记录支持范围：Windows 10/11、目标分辨率、保存目录、已售版本与升级策略。

验收物：权利确认单、源材料清单、资产哈希清单、历史版本矩阵。

### 4.2 第二阶段：优先恢复官方 PlayDRM 发行能力

当公司可取得 PlayDRM SDK、账户与密钥材料时，按厂商支持流程实施：

1. 在隔离构建机上重新构建日文版入口，使用厂商 SDK 的正式发行配置。
2. 由厂商重新签发可验证的在线或离线许可证，而不是修改旧验证逻辑。
3. 将激活、撤销、迁移与客服重置操作写入后台审计日志。
4. 用全新 Windows 用户配置文件、无网络、可网络、已激活、已撤销五种状态进行 QA。

该路线与历史用户的授权关系最兼容，应为首选。

### 4.3 第三阶段：建设新的授权发行层

若旧供应商不可恢复，新的发行层必须由公司正式开发、签名和发版。建议将授权实现与游戏
内容运行时分离：

```text
官方启动器
  -> 更新/完整性检查
  -> 公司授权服务或受签名离线许可证
  -> 日文游戏运行时
  -> XP3 内容包
```

具体职责：

| 模块 | 实现责任 |
| --- | --- |
| 官方启动器 | 检查已签名清单、安装路径、版本与必要运行库；提供错误日志和修复入口。 |
| 授权客户端 | 仅使用公司控制的 API 或已采购 SDK；验证签名、到期/撤销状态与账户绑定。 |
| 离线许可证 | 采用公司私钥签发、客户端公钥验证的许可证文件；定义迁移和失效策略。 |
| 内容清单 | 对 EXE、DLL、XP3 包及版本元数据做签名校验，防止串包和错误更新。 |
| 日文运行时 | 保持与资源包、存档和日文字体兼容；不加载汉化 DLL 或汉化 XP3。 |

新授权客户端必须是公司自行构建的发布物，接口、密钥轮换、隐私说明与崩溃收集均需有
内部文档。它不应依赖、仿真或替换旧 PlayDRM 的私有协议。

### 4.4 第四阶段：内容运行时的长期替代

并行推进 Godot 迁移项目，将已恢复的日文资源、SCN JSON 和 UI 行为纳入可读的工程资产。
这条路线可消除对旧 Kirikiri 与 PlayDRM 发行链的长期依赖，但不能代替旧版的即时授权修复。

发布前需完成：

1. 标题、设定、存读档、流程图、Extra、退出确认的视觉与交互验收。
2. 主线、全部选项分支、语音、BGM、CG、SD 与影片的资源回归测试。
3. 旧存档导入策略，或在启动器内清晰提示不能兼容的版本边界。
4. 中日文资源隔离与清单验证。

## 5. 诊断工作清单

以下诊断可立即进行，且不改变授权判定：

1. 用 Process Monitor/事件查看器记录原版失败时的缺失文件、注册表访问、网络错误和返回码。
2. 记录操作系统版本、区域设置、管理员权限、TLS 根证书、时间同步及已安装运行库。
3. 将 PlayDRM 相关文件的版本信息、签名信息、哈希和来源汇总为支持工单附件。
4. 在虚拟机中复现“已授权历史环境”与“全新环境”，比较依赖加载结果和日志，不对二进制
   做修改。
5. 将结果交由 PlayDRM 厂商或公司法务确认，决定走许可证恢复还是新授权发行层。

## 6. 构建与发布门禁

- 构建只在受控 CI 或隔离构建机执行，产物使用公司证书签名。
- 每个发行包生成 SBOM、SHA-256 清单、版本号和可复现构建记录。
- 启动器错误日志不得包含明文密钥、完整设备指纹或账户令牌。
- 授权服务需支持撤销、客服迁移、密钥轮换、最小化数据收集和故障降级策略。
- 发布前由技术、法务、发行和 QA 共同签署回归报告。

## 7. 决策建议

短期：向旧供应商申请合法的授权恢复或重签，保留当前 Kirikiri 原版作为兼容版。  
中期：由公司构建并签名新的日文发行层，具备可审计的授权与更新能力。  
长期：完成 Godot 日文重制版的内容和 UI 回归，使未来发行不再依赖已失维护的旧 DRM。

## 8. 下一步输入

要将本方案落实为正式工程计划，项目组应提供：源代码可用性、PlayDRM 合同/SDK 状态、
签名证书状态、历史用户迁移政策、目标发行平台及可用的日文资源母版。缺少这些材料时，
应先完成第 4.1 节归档和第 5 节只读诊断，不应以旧二进制补丁替代正式发行流程。
